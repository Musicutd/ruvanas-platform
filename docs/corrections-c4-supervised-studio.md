# Ruvanas Inside C4 — Supervised Studio

## Approval boundary

The ordinary `StudioProductHandoff` requires an `APPROVED` and QC-passed Studio output. That is correct for Retail, School, Online Radio, Health, Faith, and Organisations, but cannot be the first step of a Corrections contributor submission: contributor submission starts review rather than completing it. C4 therefore adds a dedicated Corrections submission path. It does not add a Corrections destination to the ordinary handoff or loosen `assertStudioRenderReady`.

The supervisor creates a facility-, programme-, contributor-, and project-scoped session. The contributor receives a time-limited random code, uses a separate browser without a staff login, and can record, edit, render and submit only that assigned project. Tier 2 uses the waveform editor; Tier 3–5 may use the multitrack mixer. Source audio in the contributor workspace is limited to the assigned project's takes. A facility manager can attach currently approved organisation-owned jingles, announcements or voice sounds as takes; licensed catalogue music is not exposed through this path. Catalogue masters, normal product destinations, publication, scheduling, and broadcast controls are absent. Server checks revalidate the organisation, Corrections entitlement, plan tier, facility, current supervisor grant, contributor state, programme state, token, and expiry. A separate `capabilityScope` governs RECORD, EDIT, RENDER, and SUBMIT. The code is displayed only at activation; a supervisor can close or revoke it.

The contributor's **Submit for Review** chooses a completed, non-preview render created during that session from its exact project and version. The existing audio worker has produced a checksum-addressed, immutable output media asset and an `IN_REVIEW` PromoVersion. `correctionsContributorRenderEvidence` verifies that render, output, checksum, status, organisation, project, and version. The submission stores the render ID, Studio project/version IDs, checksum-derived fingerprint, contributor/session/facility/programme IDs, revision, and policy versions. A unique `studioSessionId` makes retry idempotent. The output remains pending review; it is not Studio-approved and is not ready for ordinary product handoff.

The C3 Corrections Guard is the only approval authority. Review rechecks the exact submitted evidence and policy versions; the accountable supervisor is recorded as `submittedByUserId` so that supervisor cannot review their own submission. Existing staff/facility review and dual-approval rules remain. Only the Guard's `APPROVED` decision can make this submitted revision eligible for later scheduling, and the C3 scheduling lock remains in force. C4 does not create a schedule, player route, public publishing route, or external broadcast destination.

On **Changes requested**, the old `CorrectionsSubmission`, `CorrectionsReview`, render, checksum, and version remain. Staff can create a new time-limited session for the same contributor, facility, programme and project. Further edits create a new `AudioProjectVersion`; a new render and submission create the next programme revision. The old evidence is not overwritten. Concurrent active sessions for one contributor or project are blocked at both service and database levels. Expired sessions fail closed and are retired before reactivation.

## Release boundary

This is the C4 code foundation only. Its migration is additive but has **not** been run against production. Ruvanas Inside remains an unfinished product; do not production-deploy this branch, enable Render Auto-Deploy, or begin C5 as part of C4. Before a later release, run the supervised browser/audio-worker/facility acceptance scenarios against a non-production database and storage service. Keep the existing release and entitlement gates in place.
